# 20 October latency investigation

Status: r35 application changes deployed; latency target remains unresolved. This is not a claim that all replies now finish below 20 seconds.

The requested historical comparison is the 19 October morning session. The 1.864-second statistic measures model dispatch to first output, often reasoning, not a finished answer. Five short single-request follow-ups in that session finished in 13.336, 12.105, 13.491, 16.816 and 11.560 seconds (median 13.336). The initial greeting took 27.057 seconds; a four-request tool turn took 33.712 seconds. These are historical observations with a different model and context, not controlled same-input benchmarks.

## Changes and controlled evidence

- Correction lookup drives indexed event reads from correction links instead of scanning the full archive. The copied-archive query returned identical results, approximately 725 ms versus 7 ms.
- Semantic preparation selects only unindexed authorised quotations before parsing. Three native saved-input runs selected byte-identical records before and after; preparation fell from approximately 2,250 ms to 12 ms, and candidate enumeration from approximately 735 ms to 8 ms. Ranking, source access, corrections and original records remain intact.
- Fixed conversation routing and native-audio policy moved into the cacheable prefix. Short current-turn and actual-media-presence receipts remain at the tail. Reasoning is still enabled, without a new output cap.
- Byte-identical repeated audio parts become explicit references within the provider request. One full native waveform remains for each distinct content part; different formats or metadata are not combined. Source attachments and messages are unchanged. The actual selected WAV remained hash-identical while a request fell from about 3.35 MB to 1.25 MB.
- Audio serialization was tested to avoid constructing an unused image representation and repeatedly escaping encoder-produced base64. Source integrity and access checks remain mandatory.

Native regressions cover selected recall, corrections, stable session recall, cancelled-task context, capability/presence distinction, large multimodal payloads and duplicate-audio preservation. The old corrected-recall test initially failed because it asserted a superseded full-claim prompt representation; it now checks the canonical candidate interface, including correction IDs/dates, foreign exclusion, reopening, forget/restore and revocation. The initial failure is retained in private evidence.

Matched-input isolated trials of larger prompt microbatches, eight CPU threads and quantized KV cache did not justify promotion. All trial endpoints were stopped; the production model retains full-precision KV, native 65,536-token context per slot, native reasoning and the same pinned Thinking weights/projector. Instruct remains retired. Warm's conditioning, acoustic reference, pitch and synthesis helper are unchanged.

## Observed limitations

The first changed-prefix request needed a cold rebuild and took 79.405 seconds. A following warm arithmetic request finished in 9.832 seconds, but this is not representative of every workload. The actual selected audio transcribed correctly in 64.955 seconds after an unnecessary audio-restoration tool call. A word-count follow-up entered prolonged repetitive reasoning and was cancelled; this failure must not be excluded from the account of responsiveness. Changed-instruction recovery correctly quoted the ending in 13.551 seconds. Reattachment and subsequent text/memory turns still took roughly 19–24 seconds in the intermediate builds.

Reload retained the observed replies, audio cards and visible reasoning. Remembered user corrections and native audio follow-ups remained available. Acoustic adjectives generated by the model are not independently verified acoustic measurements. No all-turn latency guarantee is claimed. Full feature-film soak and broader Phase Two/Discord work remain separate open work.

Private timings, original traces and rollback snapshots are retained under the local maintenance evidence directory. Recordings, transcripts, memory excerpts and request payloads are not published.

The r33 audio and image transport tests also passed with a 1 MiB fixture containing every byte value, decoded exactly; ownership, revocation and source receipts remained enforced. Its first post-deployment audio turn took 55.928 seconds with a changed context prefix; the following short text reply, retaining native audio, took 20.242 seconds. This does not meet a claim of consistently faster conversation. The locally derived Q8_0 weights were tested separately: matched warm turns were 13.441/10.512 seconds for BF16 and 10.296/11.816 for Q8, with different generated reasoning lengths. A further Q8 follow-up took 79.120 seconds. This did not establish a reliable latency improvement; Q8 was not promoted and its endpoint was stopped. Production remains the pinned BF16 Thinking model. No additional download was used.

## r35 parser and uninterrupted browser sequence

The JSON tokenizer repeatedly scanned the entire multi-megabyte request while extracting each token. It now caches the input length and uses bounded native string copies, retaining strict escape/control validation. A retained 3.35 MB request fell from 728 ms to 20–32 ms for parsing, with 6,175 tokens unchanged. Every decoded string matched the prior decoder; all native audio hashes matched. Strict JSON, Unicode/escape/control, deep nesting, large native media and local HTTP JSON regressions passed. The intermediate unescaped-only optimization did not materially improve performance and was not deployed.

Six consecutive browser turns used the original owner archive and the exact selected Warm waveform. Preparation was 3.598–4.298 seconds, versus roughly 7.5 seconds in preceding audio turns. Results include all turns, including the slow one:

The five warm turns have median 17.700 seconds and range 12.302–54.054. The historical five short-turn median is 13.336 seconds; these are different models/contexts, so this is not a controlled speedup claim. The historical 1.864-second first-output statistic is not comparable to completed replies. Current warm decoding was about 38–40 tokens/second; long reasoning remains a major source of variability. Reload preserved all observed replies and audio cards; the Thinking disclosure still showed actual model-request, reasoning and final events. The selected voice profile was byte-identical. Original media bytes remained present in every request, including arithmetic and memory follow-ups. No transcript substitution was used.

A separate r33 tool test successfully executed attachment_list but selected an older generated audio filename from the accessible archive rather than the requested current upload. That is a retained source-selection failure, not an all-tools success claim. Cold context rebuilds, long model deliberation and this selection issue remain unresolved. The application is improved, not certified to meet a universal latency target.

## Discord 3.8 primary: six live turns, 20 October afternoon

At the operator's request, everyday Discord turns now use Qwen3.8 reasoning. The worker previously repeated live access/source REST checks after generation before privately enqueueing a reply, even though delivery independently repeats those checks immediately before POST. The redundant pre-enqueue network reads were removed. Pre-inference checks, local revision/cancellation barriers, and fresh actual-send checks remain. This is not permission caching.

Six sequential live Discord turns on the changed worker retained actual reasoning, sender labels, cross-turn recall and account separation. Five single-request replies completed in 9.900, 10.067, 12.722, 9.552 and 9.796 seconds (median 9.900). Their first model output was 1.881, 1.429, 1.453, 1.876 and 1.416 seconds (median 1.453); decoding was 29.66–30.50 tokens/second. The real system_inspect turn used two model requests and completed in 19.531 seconds. Later replies correctly retained the earlier marker and arithmetic result. There was no monotonic latency creep in this bounded sequence.

The historical short-reply median was 13.336 seconds, first-output median 1.864 seconds and decoding 31.613 tokens/second. Different prompts, context, model and transport prevent treating these figures as a controlled speedup. An earlier comparable short Discord reply before the duplicate-check removal took 13.557 seconds, but its new-token count also differed. The measurable post-stream delivery interval fell from 5.725 seconds on that turn to 2.8–3.5 seconds in the new sequence.

Cold cases are not excluded: a changed sender-prefix turn took 138.859 seconds with 48,989 uncached tokens, and a separate user conversation took 25.748 seconds with 8,720 new tokens during concurrent candidate testing. These do not meet the desired responsiveness. The new browser handoff also required a cold rebuild on its first return to 3.8. Native audio, provider-switch caching, and longer workloads remain separate acceptance work. See discord-warm-latency-2026-10-20.json for sanitized per-request measurements; complete receipts stay private.
