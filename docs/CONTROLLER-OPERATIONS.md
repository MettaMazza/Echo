# Protected controller host operations

`app/control_protected.ep` connects the isolated controller ledger to the existing protected-operation state machine. It accepts a root-owned configuration path, an action and an existing operation identity. Supported actions are initialize, inspect, apply, reconcile, rollback and rollback-reconcile. This host command is not exposed as a model tool or public HTTP route.

The command requires effective root before reading configuration or opening the ledger. Configuration and charter/inventory/policy files must pass the existing root-owned ancestry/inode checks. Configuration contains exactly ledger_directory, ledger_name, charter, inventory, inventory_sha256, policy and policy_sha256, all strings. Paths must be absolute and traversal-free; ledger_name is a single basename. Inventory and policy bytes must match their installed pins; charter bytes must match the original pinned charter. An existing private controller ledger is required; operation commands do not migrate or bootstrap one.

Apply calls the existing decision/manifest/inventory/byte checks and durable-intent exchange. Reconciliation observes the recorded physical outcome without blindly repeating the exchange. Rollback restores only the recorded preimage under the existing charter binding, and rollback-reconcile handles an interrupted rollback. No runtime archive, approval table, role or bearer credential is imported. Root invocation alone does not create Echo consent or steward authorization.

The command returns the operation status; close failures retain the preceding status in their diagnostic. Inspect currently returns verified durable state rather than complete manifest disclosure; existing disclosure functions remain separate. No service transport or principal enrolment is added by this command.

Native configuration tests and actual unprivileged command denial pass. Privileged execution through this entry point, root-ledger initialization/enrolment, service lifecycle and runtime request integration remain unfinished Step 07 work. Evidence: evidence/phase2/controller-operations-20261016/. Prior privileged bundle/launcher/ledger tests remain separate evidence and are not claimed as acceptance of this command.

## Isolated initialization

Interrupted migration/completion can resume under the same configuration; a different configuration fails closed. Ordinary operation actions still never initialize or migrate state.

## Explicit controller enrollment

`app/enroll_controller.ep` is an OS-authenticated host command for enrolling or revoking a controller steward. It uses the protected configuration loader, private existing ledger and matching completed bootstrap before any authority change. Enrollment reads a 64-character lowercase hexadecimal bearer secret from an existing root-owned, mode0600, single-link file under protected ancestry. The secret is never a command argument or printed result. Provisioning and delivery to the human interface remain separate; no runtime device or role is silently imported.

Device creation, the steward role change, immutable authority receipt and hashed canonical enrollment event commit in one transaction. Only the credential digest is stored. Exact request retries reuse the receipt without changing current authority, so retrying an enrollment after revocation cannot reactivate it. Revocation disables the credential and removes its steward role atomically. New device/credential collisions and reused change IDs with different contents fail. No HTTP or model-tool endpoint exposes enrollment.
