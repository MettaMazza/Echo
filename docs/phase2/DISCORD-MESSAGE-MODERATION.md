# Discord message and reaction moderation

Phase Two Step 15 native-qualified candidate deployed at idle for actual Discord acceptance. Adds configured-admin `discord_moderate_message` inspect, single-message delete, one user's reaction removal, one emoji cleanup and full message reaction cleanup. The rest of the community catalogue remains open.

The controller reuses Echo's authenticated Discord child/archive/journal binding, immutable tool-call ledger, frozen/current admin identity, current-channel source checks, permission snapshots and fixed-origin transport. No generic REST tool is exposed. Both requester and bot must currently have `MANAGE_MESSAGES`. Being in a group with an admin does not confer authority. Private host-tool audience restrictions remain unchanged. Guest denial identifies the requester restriction rather than calling it a system failure.

Each mutation uses the SHA-256 from a fresh inspection of the exact target message. A different response body is refused without changing remote state. Source, current role/call authority, cancellation and channel permission are rechecked before mutation. Discord does not provide a transactional conditional DELETE here: the remote message can still change after the final observation. The check detects observed changes, not an impossible guarantee against all remote races. Unknown outcomes are retained and not automatically replayed.

Reasons are required. The transport adds only a fixed `X-Audit-Log-Reason` header after URL-encoding the reason's UTF-8 bytes; no arbitrary header interface is provided. Values exceeding the documented 512 encoded-character boundary are rejected rather than truncated. Message deletion uses that audit header. Reaction moderation retains its reason in the tool request; the API does not document audit-log creation for those reaction endpoints, so no audit event is claimed. Existing callers pass an empty reason through compatibility wrappers.

Actual source inspected: Echo `post_tool.ep`, `reaction_tool.ep`, `pin_tool.ep`, `access.ep`, `rest.ep` and `permissions.ep`. The ErnosDecent bridge's `_exec_bridge_command` implements list/read/add-reaction, not message moderation; its Python transport is not imported. The prior pinned HIVE ingestion/source boundary in DISCORD-JOINED-GROUPS.md is reused without copying prompts or attributing an unverified moderation implementation to it.

Primary API references: [Message endpoints](https://docs.discord.com/developers/resources/message#delete-message), [reaction deletion](https://docs.discord.com/developers/resources/message#delete-user-reaction), [audit reasons](https://docs.discord.com/developers/resources/audit-log), [permission hierarchy](https://docs.discord.com/developers/topics/permissions#permission-hierarchy). Member/role moderation needs additional hierarchy logic and is not supplied by this message controller.

Native strict options, scope/projection under garbage collection, audit encoding/header-injection rejection and encoded-length checks passed. The authority test passed host refusal, exact current/frozen admin call, ordinary-user denial, forged calls and revocation without opening private-host audiences. Initial test parsing syntax and a missing requester-role cause code failed, were corrected, and their original logs retained. Production build passed with 36 inherited group-schema string-comparison warnings; no compiler change was made. Live permission probe confirmed existing requester and bot MANAGE_MESSAGES permission without changing grants. The controller was deployed at idle, preserving the other five worker binaries and rollback. Actual disposable-target changes and retained HTTP/audit acceptance remain pending. Only explicitly labelled disposable fixtures may be removed during live acceptance.
