# Local workspace databases

Original step 08 computation includes local databases and data transforms. `workspace_database` runs a SQLite SQL script against an explicit relative path in the current workspace, creating the database when absent. Tables, queries, joins, aggregates and updates use native SQLite through the Ernos `workspace_database` helper. This is a database workflow, not a claim that all data-transform or code/Git workflows are complete.

The original immutable tool request supplies only `path` and `sql`. Its name maps to a host-installed helper in the execution release; it cannot select another executable, workspace, environment or principal. Private and shared initiating authority use the existing execution guardian, cancellation monitor and sandbox. The helper derives its workspace from the host-set temporary-directory environment, rejects absolute/dot/parent paths and opens SQLite with READWRITE, CREATE and NOFOLLOW flags. Network and outside-workspace data access remain denied by the ordinary sandbox. Extension loading is not enabled. User SQL can change databases and other files within its permitted workspace; it is executable SQL, not a read-only search interface.

Scripts are prepared statement by statement using SQLite's tail pointer; trailing statements are not silently ignored. Output is JSON Lines with column names, typed rows, per-statement completion and a final complete/error record. Ordinary UTF-8 text is readable. Integers and reals are SQLite's text representation accompanied by a storage-class label, preserving large integers without JavaScript coercion. Blobs and text containing NUL/invalid UTF-8 use explicit hex; null remains null. Original output bytes are captured in the execution ledger and read using `workspace_output_next`. There is no added row-count or output-length cap. SQLite/platform limits and available storage still apply.

Statements autocommit unless the script starts an explicit transaction. An unfinished transaction is rolled back and reported as failure when the script ends. Earlier committed changes may remain after a later error or cancellation; inspect the database and retained output before retrying. Process status `complete` means capture ended. Script success requires raw wait status zero and the final JSON `complete` record. Failures retain stage, SQLite code and message. The database and SQLite journal/sidecar files remain workspace artifacts, and a later call reopens the same database.

`tests/tools/test_workspace_database.ep` uses the actual streamed dispatcher, guardian and sandbox to verify create/insert/query persistence, exact 64-bit integer/Unicode/blob/null/binary-text output, rollback, partial-script failure and rejected outside ATTACH. `tests/tools/test_live_database.ep` uses the primary model to create data, read SUM=60, reopen for COUNT=3, read output and complete with an intact event chain. Operational evidence is retained under `evidence/phase2/local-databases-20261016/`.

Native API references: [statement preparation and SQL tail](https://www.sqlite.org/c3ref/prepare.html), [typed result values and byte lengths](https://www.sqlite.org/c3ref/column_blob.html), [autocommit state](https://sqlite.org/c3ref/get_autocommit.html), and [open flags](https://sqlite.org/c3ref/c_open_autoproxy.html). The existing compiler and standard library were not modified.

Native sandbox and actual-model acceptance passed. An independent read-only inspection also verified persisted SUM=60 and COUNT=3.
