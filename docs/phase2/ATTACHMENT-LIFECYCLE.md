# Attachment trash and restore

Deployed 17 October 2026 as `phase2-attachment-lifecycle-20261017-022151`. This delivers reversible trash/restore within D19; it does not complete forgetting or protected erasure.

**Move to trash** appends an immutable `attachment_lifecycle` event in the source conversation. The receipt records state, previous revision, actual actor/device and original source event/digest. Current private ownership or shared-audience write access is required under the same writer transaction. Linked private devices resolve the original owner without changing the recorded actor. Stale revisions and conflicting retries are rejected; exact retry returns the existing result.

Trash prevents choosing the attachment for a new message. It does not remove original bytes, historical turn bindings, historical previews/downloads, existing project references or recall. Previously accepted submission retries still compare against their immutable binding and remain valid. Restoring appends another receipt and makes the file available for selection again, without automatically checking it for the next message. The archive event ledger is already included in ordinary database backup/restoration.

The browser's **Attachment trash and hidden files** disclosure provides Restore and explains these effects. Files hidden by the old browser-local picker remain distinct and have a local restore control. No legacy hidden item is silently converted into a global archive change. New project file choices omit trashed files; existing references remain preserved. Historical model reads intentionally remain available: this lifecycle is not a claim of forgetting.

Native acceptance (`tests/web/test_attachment_lifecycle.ep`) passed foreign denial, exact trash retry, new-submission refusal, accepted-turn retry preservation, original bytes, stale restore refusal, reopen/restore and archive integrity. Actual browser acceptance passed selecting then trashing, clearing pending selection, trash surviving reload, restoring unchecked, and unchanged original SHA256. Evidence: `evidence/phase2/attachment-lifecycle-20261017/`. One optional historical provider-selection lookup printed its existing absent-event diagnostic; test exit was zero. Local HTTP and LAN HTTPS health passed after deployment with inference preserved.

Remaining D19 work: define and enforce scoped forgetting across retrieval and derived context, expose its exact retention implications, and integrate any genuine memory/history erasure with the existing protected-change charter workflow. Do not relabel this trash feature as erasure. Broader linked-device/shared-audience browser and restore-bundle acceptance remain in the original final acceptance scope.

## Forgetting preparation

`app/web/attachment_usage.ep` provides a read-only snapshot of exact recorded turn bindings and attachment tool reads, requiring source event/digest matches for the latter. Each reference is separately filtered against the requesting device's current session access. It returns reference IDs/digests without the source text. The helper has no HTTP route or mutation capability yet and is not deployed.

`test_attachment_usage.ep` passed original binding/read discovery, foreign attachment denial, exclusion of an inaccessible reference containing the same recorded source identity, no source-text export, unchanged event count and archive integrity. Evidence: `evidence/phase2/attachment-usage-20261017/result.json`.

This is deliberately not labelled a complete derivation inventory. Automatic memories use quoted user/Echo events; manual claims retain source-event links; active recaps contain independently generated summaries. Those paths require explicit handling for broader forgetting. Maria has been asked whether forgetting should suppress direct file reads only or also past tool results and derived memories in future context. No historical data has been hidden or erased while that distinction is unresolved.

## Remaining consumer review before exposing forgetting

Source review on 17 October found that `app/projects/context.ep` validates then inserts the selected project's complete manifest into automatic context. Neither that function nor `app/projects/manifest.ep` applies attachment visibility. This preserves excluded file references in the automatic project record, although the stored file bytes are not embedded there. Before exposing the forgetting control, filter those references in the request-only project view while preserving the canonical project revision and explicit project/file reads. This is part of the existing Step 10 attachment lifecycle requirement.

The reviewed automatic graph query uses `knowledge_visible_sql`, which includes `attachment_observation_visible_sql`; group context and procedures also apply the exact source-event filter. `recap_source_record` substitutes an exclusion receipt for original tool-result content. These are source observations, not new live acceptance claims. Text quoted into separately authored user/Echo messages does not gain attachment provenance merely through matching wording; do not imply semantic erasure of every paraphrase.
