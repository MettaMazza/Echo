# Discord channel administration

Step 15 channel controller passed the four-turn labelled live acceptance on 22 October, including explicit recovery after retained native failures. The native `discord_channels` controller implements paginated same-audience list/inspect, text/voice/category/forum creation, name/topic/slowmode/position/voice-setting edits, category placement, and deletion from another control channel. Permission-overwrite editing and broader thread/member/role/community/voice catalogue remain open. This is not full Step 15 completion.

The controller reuses the authenticated Discord child/archive/journal/run/call binding. A configured admin and live requester/bot MANAGE_CHANNELS are required. Channel creation additionally checks guild-level permission. Source identity, current access, revocation, cancellation and admitted Gateway source are rechecked. Host-private tool audience restrictions remain unchanged. Unknown transport results retain original receipts and do not imply no effect.

New channels copy the originating channel's explicit permission overwrites. Metadata is released only for the same guild and an exact matching overwrite representation. This is conservative: equivalent but differently represented permission sets can be withheld. Mismatch does not mean absence. Private-channel metadata is not dumped into a public conversation merely because an admin requested it. Parent categories require matching audience, identity, type and permissions. Explicit permission changes are not exposed by this candidate.

Edit/delete requires a fresh raw-body SHA from inspect. Discord offers no transactional compare-and-mutate operation; changes after observation remain possible. A durable immutable per-run/call mutation claim precedes network transmission. A repeated call cannot replay an uncertain create/edit/delete, including after restart. Recovery inspects original results and current Discord state. Deleting the current control channel is refused with direction to issue the request from another authorised channel.

Actual source inspection reused Echo access, permission, audited REST, post/pin/moderation and source-binding controllers. ErnosDecent `discord_bridge.py` thread creation at 1487 and 3420 was read: its transient trace cleanup/prompt branding was not imported. The pinned HIVE ingestion inspection in DISCORD-JOINED-GROUPS.md establishes its narrow source boundary, not an unverified channel-management implementation.

## Live failure retained and recovery under qualification

The first actual-model turn created the disposable category and child with separate HTTP 201 receipts, then its child process exited with signal 11 during category inspection. The supervisor stopped rather than replaying completed mutations. Both creation bodies and hashes were independently compared; this is partial evidence, not a live pass. The isolated same read succeeded, so that smaller check does not reproduce or explain the whole failure.

Review found unrooted provider-items iteration lists in the shared permission and recipient paths. Merely naming them did not produce generated GC roots; that intermediate repair was rejected before deployment. An explicitly rooted container now retains the lists. Generated-code proof and 500 paired permission checks spanning collection are retained. Causal attribution to this fault remains provisional until the full live path succeeds. No compiler changes were made.

Explicit interrupted-read maintenance now admits only validated channel inspect/list alongside the existing message-read tool. It records an unavailable original read outcome without network replay, and leaves unstarted reads for normal current authorization. Native tests passed read, channel read, mutation refusal, channel-mutation refusal, revoked authority, cancellation and repeated recovery. Snapshot recovery and then the confirmed-exited live child's recovery passed. Existing channel creations were not repeated. Replacement builds and recovered multi-turn acceptance remain pending.

The actual restart additionally exposed a `ready`-only entry gate: even an explicitly reconciled tool phase with only unstarted reads was held. The gate now requires an interruption receipt for the exact current parent, no running/uncertain calls, and only queued message reads or channel inspect/list. Every remaining read still goes through its normal current authority/source checks. Native recovery tests pass; a mistaken response-suffix comparison was caught by the positive fixture and corrected before deployment. The maintenance CLI records explicit reclamation of the known stopped recovery state under its exclusive archive lock. The saved live request was relaunched with the correction; its final multi-turn outcome remains pending.

## Saved follow-ups during recovery

The original crash also exposed a separate queue defect: later messages received `session-active` before admission, but the connector treated that result as terminal. The corrected queue retains that pre-admission result as retryable, preserves conversation order and cancellation, and keeps unrelated conversations eligible. A `run-recovery-required` predecessor blocks subsequent messages in its conversation without becoming automatically replayable. Queue position and refresh use the same pending states. Existing stored `session-active` messages become eligible through normal source/authority checks; no message body or accepted run is rewritten. Native tests passed persisted session-contention retry, pending queue position, independent-channel progress while a predecessor requires recovery, and cancellation of a waiting message. The saved live sequence remains pending.

Rebuilding all connector roles caught a missing direct import of the read-recovery guard in the shared turn module. It is now explicit rather than relying on the agent executable's transitive imports. Failed builds were retained and not deployed.

The next real run exposed a second fault inside the runtime `string_split` implementation itself (`append_list`/`realloc` during list construction). Rooting a returned list cannot protect that internal construction. The application header parser therefore now scans its retained input directly, without `string_split` or an iteration list. The same native collection test passes, including final unterminated headers, empty input, final HTTP block selection and conflict refusal. The compiler/runtime are unchanged. The failed intermediate repair remains recorded; live acceptance of the scanner is pending.
